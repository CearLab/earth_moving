2D ALGORITHM AND BENCHMARK REVIEW
7 November 2026

Scope
Read the publication experiment section and table sources, the three detailed
benchmark exports, the September 16 analysis, both summary reports, the benchmark
runner/tracker/configuration and plotting code, and the core path, heat, update
and spillage routines. Recomputed descriptive summaries from saved records.
No benchmark campaign was launched and no original source file was changed.
Source paths and SHA-256 hashes are in source_manifest.json. This is an inspection
of the supplied files; the archive does not identify an immutable code revision
proving that every historical record used the exact source now present.

Main finding
There is substantial existing 2D computational evidence worth explaining, but
the archive mixes first construction, cached calls, instrument overhead and
different operation families. The evidence supports a historical computational
study, not yet a clean measurement of every claimed optimization.

MEASUREMENT FINDINGS
1. Cache reset: benchmark_runner.py:88 calls calculate_strategic_fields_now on
   the same demo across repeats. Its optional clear_all_cached_data method is
   absent from the supplied orchestrator. The demo alias at :209 calls
   calculate_on_demand, guarded by absence of env._fields_calculated. The first
   call sets the flag; later calls skip construction. This explains the observed
   first/repeat pattern in the inspected code. It is not ordinary CPU warm-up.
2. Timer boundary: PerformanceTracker.measure_operation starts the timer before
   CPU/RSS reads and tracemalloc snapshots. It stops after the callback. Thus
   recorded time includes instrumentation before computation. The full callback
   additionally invokes garbage collection inside the timer. Console prints
   remain in called routines. An isolated kernel, stabilized warm-up protocol
   and exclusion of all I/O are not established by this source.
3. Update timing excludes pre-executed pushes, which is appropriate for a
   computation measure. But the wrapper also restores state and gathers
   metrics inside its timed callback. It deep-copies the grid separately from
   shallow-copied cell lists and affected lists. That risks inconsistent cell
   identity. Restored backups are assigned directly and may be mutated. A
   common immutable post-action snapshot is needed for a controlled comparison.
4. Custom metrics: run_benchmark tries to attach callback metadata before the
   context manager creates the current metrics record. All 9,200 saved custom
   metric dictionaries are empty. Consequently affected-cell counts, update
   success flags and path statistics cannot be recovered from those fields.
   A callback returning a failure dictionary is not necessarily a failed
   runner scenario, so 'zero failed scenarios' is not an update-correctness test.
5. Flags: use_affected_only_updates is accepted by create_simulation_quick but
   is not applied to an environment control in that function. The matrix test
   calls field construction, not a paired update/full routine. The saved
   suffix/matrix parameters omit the optimization flags. These facts prevent
   treating their labels as verified optimization ablations.
6. Memory: memory_peak_mb is max of sampled endpoint RSS values, not a sampled
   high-water mark throughout each operation. The optional monitoring thread
   is not started by run_benchmark. The 410 MB reported average is an endpoint
   process-footprint summary and does not prove a peak bound or absence of leaks.

PUBLICATION / ANALYSIS RECONCILIATION
The publication table gives full medians 420/980/1910 ms and update medians
49/129/273 ms for grids 25/45/65. These do not match the selected archive's
pooled means or medians. No matching seed-level bootstrap calculation was
identified. Retain them as previously reported, pending provenance reconciliation.

The report's 19.49055% and p=0.0091628 are stored in spillage_analysis.comparison:
With Spillage n=800 versus Without Spillage n=6480. They are not stored as a
suffix-reuse test. The analyzer uses Welch's independent t-test, not Wilcoxon.
Missing use_spillage fields default to false, pooling unrelated operation
families into the second group. Therefore even the spillage attribution is
confounded. Do not transfer this percentage or p-value to continuation reuse.

The original time_per_object_efficiency graph uses the analyzer's full retained
dataframe, without filtering to construction. Its 30-grid/55-object points
come from the matrix cohort. The curves visibly decrease for several grids;
the graph does not establish constant per-object construction cost.
R-squared 0.9881097 is from an ordinary linear fit to five grid-size pooled
mean times, not evidence of a log-log slope 1.03 for construction. Polynomial
fit labels do not establish asymptotic complexity.

RECOMMENDED CLEAN BENCHMARK (SPECIFICATION ONLY)
Freeze source/configuration and record hashes, environment, CPU and concurrency.
Separate cold construction, intentional cached queries and selective updates.
Restore one canonical object graph per replicate; verify counts and identity.
Time explicit computational stages with logging/profiling outside the interval.
Predeclare warm-up and repetition handling; aggregate within environment first.
Pair selective and full rebuilding on exactly the same post-action snapshot.
Compare candidate paths, values, headings, heat and connector decisions before
reporting a speedup as equivalent work. Include decreased rewards and spill.
Test reuse on/off in raw mode with an effective flag, same inputs and cache
reset. Record node expansions, queue size and returned-path accounting.
Persist seed, flags, failure state and affected-source fraction in every record.
Use paired environment-level uncertainty and distinguish memory RSS from peak.
Keep this future validation separate from the recovered historical results.
